## 1. 지금 구조 (근거)

| 영역 | 현재 | 다중 교사에서 문제 |
|---|---|---|
| 교사 로그인 | `classroom_settings`(1행, `id=1`)의 비밀번호 하나 → `teacher_login` → `teacher_sessions`(8시간) | 교사 구분 불가. 세션이 어느 학급 것인지 모름 |
| 교사 식별자 | `pc_actor`가 교사를 항상 `id:'teacher'`로 반환 | 요청 중복방지 키(`petclass_requests.id = actor.id||':'||requestId`)가 교사끼리 충돌 |
| 학생 | `classroom_students.student_no` 0~25 **전역 유일**, `access_code` 4자리 **전역 유일** | 학급마다 1~25번을 못 만듦. 4자리 번호 공간 1만 개를 모든 학급이 나눠 씀 |
| 역할 | `classroom_roles.id`('leader' 등)가 전역 PK, 학생·지원·추첨 기록이 이 ID 참조 | 학급마다 다른 역할 불가 |
| 상점·미니게임 | `classroom_shop_items`, `petclass_products`, `petclass_games`가 전역 | 모든 교사가 상품·확률을 공유 |
| 설정 | 역할 지원 마감일·교사 비밀번호가 `classroom_settings` 1행 | 학급별 마감 불가 |
| 학급 이름 | `pc_state`·`lib/backend.ts`에 `'1학년 3반'`, CSV 파일명 `1학년_3반_…` | 고정 |
| 학급 전용 규칙 | 화면 코드의 `POINT_OPTIONS`(포인트 사유 14개), `PAYROLL_RULES`(월급 감액 12개, `leader`·`bank`·`audit`·`reading`·`device` 역할 ID에 묶임), 다독이 추천도서 보너스(`reading` 역할), 자리 선정권 월 3회(`seat` 상품) | 다른 반에는 맞지 않음 |
| 함수 | `public`·`private` 함수 30개 중 학급 하나를 가정하는 함수 13개(`between 1 and 25`, `id = 1`, 특정 역할·상품 ID), 교사 함수 18개는 `require_teacher(token)`만 확인(학급 개념 없음) | 거의 모든 함수에 학급 범위 추가 필요 |

**유리한 점**: 브라우저는 DB에 직접 접근하지 않음. anon이 실행 가능한 함수는 `petclass_gateway` 하나뿐이고, 서버 비밀키로만 호출됨 → 학급 범위를 게이트웨이 한 곳에서 일관되게 걸 수 있음.

참고(Boony): 교사·관리자는 Supabase Auth 이메일/비번, `profiles.role`(admin/teacher) + `approval_status`, 자유 가입 후 관리자 승인, 비번 분실 시 관리자가 재설정(서비스 키), 학생은 익명 로그인 + 학급별 8자 코드, 격리는 RLS + `owns_board()` 류 함수.

## 2. 범위

**포함**
- 교사 가입·로그인(이메일/비번), 관리자 승인, 관리자 화면
- 교사가 학급 만들기: 학급 이름, 학생 수, 1인 1역 역할(이름·정원·월급·순서), 역할 신청 마감일
- 학생 입장(학급 + 4자리 개인 번호 유지)
- 학급별 데이터 완전 분리(학생·포인트·역할·상점·미니게임·펫·기록)
- 내 반(1학년 3반) 데이터를 내 계정 소유 학급으로 이전

**제외(v1)**: 공동 담임·부담임 공유, 학생 이름 저장, 학교 단위 관리, 유료 기능. 데이터 구조는 나중에 추가할 수 있게만 열어 둠.

## 3. 핵심 설계 결정 (권장안)

### 3-1. Boony를 "그대로" 옮기지 않고 섞는다
- **채택**: 교사 신원 확인만 Supabase Auth(이메일/비번) 사용. 로그인 후에는 지금처럼 **서버가 발급하는 HttpOnly 세션 쿠키 + 게이트웨이** 구조 유지.
- **이유**
  1. 이 앱은 Next.js가 아니라 vinext. Boony가 쓰는 `@supabase/ssr` 쿠키 연동이 그대로 동작한다는 보장이 없음. 서버에서 Supabase Auth REST를 직접 호출하면 의존성이 거의 없음.
  2. 지금 모든 데이터가 게이트웨이 하나로만 오가므로, RLS로 전면 재작성(사실상 앱 재작성)보다 "게이트웨이에서 학급 범위 강제 + 복합 외래키로 교차 참조 차단 + 격리 테스트"가 작업량·위험 모두 작음.
  3. 학생은 Supabase 계정이 필요 없음(익명 로그인 불필요). 지금 방식 그대로.
- **화면은 Boony처럼**: 로그인 화면에서 "학생" / "선생님" 분리. 선생님은 이메일·비번, 학생은 번호.

### 3-2. 흐름
```
[교사 가입] 브라우저 → /api/auth/signup → Supabase Auth signUp → (DB 트리거) profiles 행 생성: pending
[관리자 승인] /admin → 게이트웨이 'adminReview' → profiles.approval_status = approved
[교사 로그인] 브라우저 → /api/auth/teacher → Supabase Auth 비번 확인(서버↔Supabase 직접) → user id
             → 게이트웨이 'teacherLogin'(승인 여부 확인) → petclass_sessions(teacher_id, class_id) → HttpOnly 쿠키
[학생 로그인] 브라우저 → /api/farm 'login'(학급코드 + 4자리) → 게이트웨이 → petclass_sessions(student_id, class_id) → 쿠키
[모든 요청] 쿠키 → pc_actor = {role, id, teacherId, classId} (요청마다 계정 승인·존재 여부 재확인) → 모든 조회·변경에 classId 강제
```
- `classId`는 **항상 세션에서만** 가져옴. 요청 본문의 학급 값은 절대 믿지 않음.

## 4. DB 설계

### 4-1. 새 테이블
```sql
private.profiles(
  id uuid primary key references auth.users on delete cascade,
  email text not null, display_name text not null,             -- 화면 표시용 "윤○○ 선생님"
  role text not null default 'teacher' check (role in ('admin','teacher')),
  approval_status text not null default 'pending'
    check (approval_status in ('pending','approved','rejected')),
  review_note text, created_at timestamptz default now(), reviewed_at timestamptz)
-- auth.users insert 트리거 → profiles(pending) 자동 생성. 관리자 지정은 SQL로만(Boony와 동일, 앱에서 승격 불가)

private.classes(
  id uuid primary key default gen_random_uuid(),
  teacher_id uuid not null references private.profiles,
  name text not null check (char_length(btrim(name)) between 1 and 20),  -- 반 이름, 형식 자유("1학년 3반", "개멋진반")
  -- 반 이름 중복 금지: 공백 제거·대소문자 무시 기준 unique index (학생이 목록에서 헷갈리지 않게)
  student_count smallint not null check (student_count between 1 and 40),
  application_deadline timestamptz,
  features jsonb not null default '{}',      -- 다독이 보너스 등 학급별 켜기/끄기
  created_at timestamptz default now(), archived_at timestamptz)

private.admin_audit(id, admin_id, action, target, detail jsonb, created_at)   -- 승인·거절·임시 비번·학급 초기화·계정 삭제 기록
```
`private.class_point_presets`(학급별 포인트 사유), `private.payroll_rules`(전체 공통 월급 조정 규칙, 관리자만 관리) 추가 — 7장 참고.

### 4-2. 기존 테이블 변경
| 테이블 | 변경 |
|---|---|
| `classroom_students` | `+ class_id`(not null), `+ active boolean default true`. 유일 제약 `(student_no)`·`(access_code)` → `(class_id, student_no)`·`(class_id, access_code)`. 번호 범위 0~40(0 = 학급별 테스트 학생) |
| `classroom_roles` | `+ class_id`, `+ rule_key text null`(특별 규칙 역할 표시: leader·audit·bank·reading·device). PK `(id)` → `(class_id, id)`, 이름 유일도 학급 단위. 새 역할 id는 서버가 생성 |
| `role_applications`, `role_lottery_audit` | `+ class_id`. 학생·역할을 **복합 외래키 `(class_id, …)`**로 참조 → 다른 학급 역할에 지원하는 행 자체가 DB에서 불가능(Boony 방식) |
| `classroom_shop_items` | `+ class_id`, PK `(class_id, id)`. `+ monthly_limit int null`(학급 전체 월 판매 한도 — 자리 선정권 "월 3회"를 일반 기능으로) |
| `petclass_products`, `petclass_games` | `+ class_id`, PK에 포함. 새 학급 생성 시 펫 상품 4개·게임 3개 기본값 복사 |
| `petclass_logs` | `+ class_id`(교사 작업 로그는 학생이 없어서 학급을 따로 기록해야 함) |
| `petclass_sessions` | `+ teacher_id`, `+ class_id`. `teacher_sessions`는 폐기(교사 세션도 여기로 통합) |
| `petclass_attempts` | 키를 `학급 + 학생번호 + IP`(학생), `IP + 이메일`(교사)로. 실패할수록 대기 시간 증가(잠금 없음). 성공 시 IP 전체 초기화하던 동작 제거 |
| `petclass_requests` | 키 앞부분을 교사 uuid로(현재 `'teacher'` 고정 문자열 → 교사끼리 충돌) |
| `classroom_settings` | `classes`로 옮긴 뒤 삭제. `teacher_password_hash` 폐기 |
| `point_entries`, `orders`, `game_plays`, `farms` | 학생을 거쳐 학급이 정해지므로 컬럼 추가 불필요. 원장 조회가 느려지면 `class_id` 비정규화 + 인덱스(선택) |

### 4-3. 함수 변경
- `pc_actor`: `{role, id(교사=profiles.id), teacherId, classId, name}` 반환. 요청마다 `approval_status = 'approved'` 재확인 → 계정이 삭제되면 다음 요청부터 즉시 차단.
- `pc_state`, `petclass_gateway`의 모든 액션: 학생 목록·원장·주문·로그·상품·게임 조회와 변경에 `class_id = actor.classId` 조건.
- 교사용 기존 함수 18개(`teacher_*`, `classroom_snapshot`, `submit_role_applications`, `auto_assign_roles`, `teacher_lottery`…): 인자를 `p_token uuid` → `p_class uuid`로 바꾸고 `pc_legacy`가 세션의 학급을 넘김. `between 1 and 25`, `id = 1`, `'reading'`, `'seat'` 하드코딩 제거.
- 쓰지 않는 옛 함수 정리: `student_purchase`, 2인자 `teacher_run_payroll`, `teacher_login`, `teacher_change_password`, `require_teacher`.
- 새 게이트웨이 액션: `teacherLogin`, `classCreate`, `classUpdate`(이름·마감일·학생 수), `roleUpsert`/`roleDelete`/`roleReorder`, `classList`(로그인 화면용 반 이름 목록), `adminList`/`adminReview`, `adminSetPassword`(관리자 임시 비번 지정).

## 5. 계정·입장 흐름 상세

### 5-1. 교사
1. **가입** `/signup`: 이메일, 비밀번호(8자 이상), 표시 이름, **반 이름**(형식 자유 1~20자, 예: "1학년 3반"·"개멋진반", 이미 있는 이름이면 안내). **이메일 인증 없음**(결정됨) — 이메일은 로그인 ID + 관리자가 연락할 때만 사용. 개인정보 안내 문구(학생 이름은 저장하지 않음). Cloudflare Turnstile은 선택(Boony처럼 키가 있을 때만 표시).
   - Supabase 설정: Authentication → Email → "Confirm email" 끔(대시보드에서 1회, 사용자가 직접). 인증 메일이 안 나가므로 기본 메일 서버 제한과 무관.
   - 인증이 없어서 남의 이메일로도 가입 신청은 가능 → **관리자 승인 때 실제 선생님인지 확인하는 것이 유일한 관문**.
2. **승인 대기 화면**: 대기·거절(사유 표시) 상태별 안내.
3. **관리자 승인**(결정됨: 관리자가 직접): `/admin`에서 대기 목록 → 승인/거절.
4. **로그인**: 이메일·비번. 학급이 없으면 학급 만들기 마법사로 이동.
5. **비밀번호 분실**: 메일을 보내지 않으므로 **관리자가 임시 비밀번호를 지정**(Boony 방식) → 교사는 로그인 후 "내 계정 비밀번호 변경". 이 기능에 `SUPABASE_SERVICE_ROLE_KEY`(서버 전용) 필요.
6. **비밀번호 변경**: 학급 관리의 "교사 비밀번호 변경"을 "내 계정 비밀번호 변경"으로 교체(현재 비번 확인 후 Supabase Auth 갱신).

### 5-2. 관리자 (결정: 교사와 분리된 별도 계정, 권한 최소)
- **관리자 계정은 학급이 없음.** 로그인하면 `/admin`만 보임(Boony와 같은 구조). 관리자 지정은 SQL로만(앱에서 승격 불가).
- **할 수 있는 것 (이것만)**
  1. **가입 승인·거절**: 대기 목록(이름·이메일·반 이름·가입일). 거절 시 사유 입력(선택) → 교사 승인 대기 화면에 표시.
  2. **임시 비밀번호 지정**: 비밀번호를 잊은 선생님용. 학급 데이터는 그대로. 교사는 로그인 후 "내 계정 비밀번호 변경"으로 바꿈.
  3. **학급 데이터 초기화**: 계정·학급 설정(반 이름·학생 수·역할·상품·미니게임 설정·포인트 사유)·학생 4자리 번호는 남기고 학생 포인트·펫·역할 배정·역할 지원·구매·게임 기록·로그를 비움. 새 학기용.
  4. **계정 삭제**: 선생님 계정과 그 학급의 모든 데이터를 통째로 삭제. 탈퇴·전근 처리용.
  - 3·4번은 반 이름을 직접 입력해야 실행되는 확인창 + 실행 직전 해당 학급 데이터를 JSON으로 내려받는 버튼(되돌릴 수 없으므로).
- **할 수 없는 것**: 학급 안의 데이터 보기·수정(학생 포인트·펫·역할 등), 학급 설정 변경, 학급 만들기. 계정 정지 기능도 두지 않음(필요하면 계정 삭제).
- 관리자 작업은 모두 `admin_audit`에 기록(누가·언제·무엇을).
- 교사 이메일은 승인 목록에서 확인 용도로만 보임. 연락은 관리자 본인 메일로.

### 5-3. 학생 (결정: 반 이름 선택 + 개인 번호 4자리)
- 로그인 화면 "학생" 탭: **① 반 고르기**(승인된 교사의 반 이름 목록) → **② 4자리 번호 입력**. 학급 번호를 외우거나 칠 일 없음.
  - 목록 정렬: 숫자를 숫자로 읽는 정렬(1학년 1반 → 1학년 2반 → … → 2학년 1반), 그다음 자유 이름(가나다순). 반이 많아지면 위에 검색칸.
  - 기기가 마지막으로 고른 반을 기억해서 다음엔 미리 선택돼 있음. 바꾸려면 다시 고르면 됨.
  - 로그인 직후 상단에 **"개멋진반 · 7번"**을 크게 보여 줘서 다른 반을 고른 실수를 바로 알아챌 수 있게.
  - 목록에는 **승인된 교사 + 학급 만들기를 끝낸 반**만 보임. 대기·거절된 교사의 반은 숨김.
- 개인 번호는 반 안에서만 유일 → 반마다 1만 개 독립. 반 이름은 누구나 볼 수 있는 값이고, 실제 비밀은 4자리.
- **보안 메모**: 한 반(25명)을 정해 찍으면 한 번에 맞힐 확률 25/10,000 = 0.25%로 지금과 같음. 그래서 속도 제한이 책임짐. 반 전체를 잠그는 방식은 장난으로 다른 반 전체를 막을 수 있어서 쓰지 않음:
  1. 같은 IP에서 같은 반 실패: 5회부터 시도 간 대기 시간 증가(1초 → 2초 → 4초 … 최대 30초)
  2. 같은 IP 전체 실패: 15분 300회 넘으면 그 IP만 대기(학교 공유 IP에서 여러 반이 동시에 오타를 내도 넉넉하게)
- 공용 기기: 기존 "학생 전환 / 나가기" 유지.

## 6. 학급 만들기·설정

### 6-1. 마법사(첫 로그인)
1. 반 이름(가입 때 입력한 값이 미리 채워짐, 수정 가능)
2. 학생 수(1~40)
3. 역할 목록: **기본값 = 지금 운영 중인 체제 그대로**(결정). 13개 역할(반장 2·지킴이 1·통장이 1·다독이 2·깔끔이 3·칠판이 3·가통이 4·기록이 2·디벗이 1·알림이 2·의견이 1·체육반장 1·출석이 2 = 정원 합계 25)과 월급, 역할별 특별 규칙까지 함께 생성.
   - 교사가 하는 일: 역할 빼기, **역할별 인원수(정원)** 조정, 월급·순서 조정, 일반 역할(특별 규칙 없는 역할) 추가.
   - 정원 합계 / 학생 수 표시(예: 24/25). 경고만 하고 막지는 않음.
   - 표 바로 아래에 눈에 띄는 안내 상자(노란 배경·굵은 글씨, 학급 관리의 역할 편집 화면에도 동일하게):
     > **특별한 규칙이 적용되는 역할 추가에 대해서는, 관리자(윤0후T)에게 문의하세요**
4. 역할 신청 마감일
5. 확인 → 생성: 학생 1~N번(학급 안에서 겹치지 않는 4자리 무작위), 테스트 학생 0번(100,000P, 학생 화면에 숨김), 펫 상품 4개·미니게임 3개 기본값. 이때부터 학생 로그인 목록에 반 이름이 나타남
6. 완료 화면: 학생 번호표(CSV·인쇄용, 반 이름 함께 표기)

### 6-2. 이후 수정(학급 관리 탭에 추가)
- 반 이름(중복 확인)·마감일 수정
- **학생 수 늘리기**: 뒷번호로 추가. **줄이기**: 뒷번호부터 "비활성"(로그인 불가·명단에서 숨김, 포인트·펫 기록은 보존). 다시 늘리면 복구
- **역할 편집**: 정원·월급·순서 변경, 일반 역할 추가·이름 변경, 역할 삭제(배정된 학생은 "미배정"으로 돌리고 확인창). 정원을 현재 배정 인원보다 줄이면 막음.
  - 특별 규칙 역할(반장·지킴이·통장이·다독이·디벗이)은 "특별 규칙" 표시가 붙고 **이름 변경 불가**(규칙 문구가 역할 이름을 가리키기 때문). 정원·월급 조정과 삭제는 가능.
  - 특별 규칙 역할 추가는 교사 화면에 없음 → 위 안내 상자. 관리자 화면(또는 SQL)에서만 학급에 추가.
- 기존 기능(학생별 번호 수정·재발급, 역할·지원 초기화) 유지

## 9. 보안·운영
- **격리 테스트(PGlite, 기존 방식 확장)** — 머지 조건
  - 교사 A 세션으로 B 학급의 학생·원장·상품·게임·역할을 읽기/수정 시도 → 전부 거부
  - 두 학급에 같은 4자리 번호가 있어도 각자 자기 학급으로만 로그인
  - 삭제된 교사 계정의 세션은 다음 요청부터 차단
  - 교사 둘의 요청 번호가 같아도 충돌 없음
  - 다른 학급 역할에 지원하는 행은 복합 외래키로 생성 불가
- **속도 제한**: DB 기반이라 서버 인스턴스가 여러 개여도 공통(Boony의 메모리 방식보다 강함)
- **학급 간 간섭 점검(추가)**
  - 모든 서버 동작을 "교사 A 세션 + B반 ID"로 실행해 보는 테스트를 동작 목록에서 자동 생성 → 하나라도 통과하면 실패(가장 큰 위험: ID로 다른 반 기록을 수정·환불)
  - 상품 이미지 주소에 학급 포함(학급마다 같은 상품 키 `food-s` 등이 생기므로)
  - 자리 선정권 같은 월 판매 한도의 잠금·집계를 학급 단위로(지금은 전체 공통 잠금 번호·상품 이름으로 전체 집계)
  - 학급당 이미지 개수·용량 상한(무료 DB 500MB를 모든 반이 공유)
  - 전체 공통 월급 규칙표 수정 시 "모든 학급에 적용" 경고
- **비밀값**: 기존 `PETCLASS_API_SECRET` 유지 + `SUPABASE_SERVICE_ROLE_KEY`를 Vercel 서버 전용으로 추가(관리자 임시 비밀번호 지정·계정 삭제용). 브라우저 코드에 절대 노출 안 함
- **용량(무료 한도)**: DB 500MB. 상품 이미지를 DB에 직접 저장 중(한 장 최대 약 400KB) → 학급이 수십 개를 넘으면 Supabase Storage(1GB)로 옮기는 단계 추가 검토
- **개인정보**: 교사 이메일만 수집, 학생은 번호만. 가입 화면에 안내 문구
- **백업**: 전환 직전 모든 학급 데이터 JSON 내보내기(무료 플랜은 직접 받을 수 있는 백업이 없음)
